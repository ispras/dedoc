# Архитектура распараллеливания пайплайна

> Черновик спецификации. Раздел «Задачи» и «Конфигурация задачи» — со слов заказчика.
> Ниже, после маркера, будет дописано объяснение.

## 1. Задачи пайплайна, с которыми работаем

Первое, что делаем, — выделяем задачи, с которыми работаем в плане распараллеливания.
Дальше речь **только** об этих задачах. Все они допускают **параллелизм по страницам**.

### Этап предобработки (preprocessing)

Задачи могут следовать друг за другом **в разном порядке**, и какие-то из них могут **вовсе не выполняться**.
Порядок и состав **задаются через конфиг, а не жёстко в коде**. Эти задачи **предшествуют** тому, что идёт дальше.

- **binarize** — бинаризация
- **orientation** — проверка ориентации страницы (повороты на 90 / 180 / 270 градусов)
- **skew** — корректировка угла / перспективы

### Этап обработки (processing) — самый тяжёлый

- **layout**
- **OCR**
- **table** — работа с таблицами

### Задачи до и после всех перечисленных

Менее важные — надо просто чтобы они работали. Обычно они работают **со всем документом**.
**Менять их не надо.**

## 2. Конфигурация задачи

Каждая из перечисленных задач конфигурируется следующим набором полей.
По этому конфигу оркестратор понимает, **какому воркеру и как** передать конкретную задачу.

- **CPU / GPU** — специфична ли задача для CPU или GPU.
- **batch size** — размер батча.
- **thread / process** — задача сама выделяет отдельный процесс, или её, возможно, надо **обернуть** во что-то для этого.
- **page / document** — гранулярность. Для всех перечисленных задач — **page**; поле введено для **унификации**,
  чтобы этим же конфигом в итоге описать **вообще весь пайплайн**.
- **blockers** — список задач, исполнение которых **блокирует** исполнение этой задачи.
  Через список блокеров и будет строиться **граф исполнения**.

## 3. Структура задачи

Сама задача характеризуется структурой, в которой есть:

- **входные данные** — данные для обработки;
- **конфиг для обработки** — например, `bbox` для обработки только части реальной страницы;
- **состояние обработки** задачи — на всякий случай, может, и не нужно;
- **приоритет** обработки;
- **номер страницы** (возможно);
- **выход** — то, что получилось на выходе.

## 4. Наборы задач у оркестратора

Задачи лежат в нескольких наборах:

- **«готово к обработке»** — в начале сюда кидаются задачи **без блокеров**; список обновляется,
  когда выполненная задача **разблокирует** следующую за ней;
- **«обработано»** — возможно, потом будет удалён, но пока пусть будет для отладки;
- **«ждёт обработки»** — тут лежат пока **неразблокированные** задачи.

## 5. Планирование

- Оркестратор выбирает **случайную** задачу из тех, у кого **приоритет выше**, и отправляет её свободному воркеру.
- Если тип воркера **GPU** — он складывает задачи, пока не наберётся **батч**, и только потом исполняет.

## 6. Унификация

- Задачи работают по **примерно одному интерфейсу** — функция `process`, в которую передаётся конфиг и входные данные.
- Все задачи должны уметь работать **в отдельном процессе**, т.к. нам надо, чтобы процессор не простаивал из-за **GIL**.

## 7. Разрешённые решения (ответы на вопросы)

1. **Передача данных — shared memory** (скорость важна): картинки страниц в разделяемой памяти, между процессами ходят ссылки, не pickle.
2. **1 GPU-воркер + много персистентных CPU-воркеров.** Под-вопрос загрузки моделей в GPU-воркер — см. рекомендацию ниже.
3. **`thread/process` характеризует САМУ задачу** (а не действия оркестратора):
   - `process` — задача **сама создаёт себе процесс**, дополнительных обёрток не нужно (напр. OCR/Tesseract, tabby/Java);
   - `thread` — так **не умеет**, работает максимум в отдельном треде.
   *(Следствие для оркестратора: `thread`-задачу он поднимает в персистентный CPU-**процесс-воркер**, чтобы обойти GIL; `process`-задаче хватает потока, т.к. она форкается сама.)*
4. **GPU-батч — из однотипных задач + таймаут** (против простоя и проблемы последних страниц).
5. **Приоритет статичный: чем дальше задача от старта в графе, тем она приоритетнее** (чтобы CPU быстрее доходил до GPU-задач). **RAM** ограничиваем **числом одновременных воркеров** — невзятая в работу задача памяти ест мало.
6. **Упавшая задача = warning и РАЗБЛОКИРУЕТ дальнейшие**; на вход зависимые получают **не пустое, а тот же вход**, что был у упавшей задачи (pass-through).
7. **Пока только per-page.** Whole-document — потом.
8. **`state` оставляем для отладки; выбор задач — пока по порядку страниц** (нагляднее), random позже.

### Рекомендация по GPU-воркеру
**1 персистентный GPU-воркер, держащий все GPU-модели загруженными одновременно** (orientation EfficientNet-B0 — маленький, layout RT-DETR — вместе влезают в типичный VRAM), с отдельными очередями-батчами **по типу задачи**. Плюсы: одна CUDA-сессия, по одной копии весов, без межпроцессной борьбы за единственный GPU. Вариант «N воркеров под каждую сеть + активация нужного» оправдан **только** если VRAM не вмещает все модели сразу (не наш случай).

### Предлагаемое разнесение задач по воркерам *(подтвердить)*
| задача | resource | exec_mode | воркер |
|---|---|---|---|
| binarize | CPU | thread | CPU-процесс-воркер |
| skew | CPU | thread | CPU-процесс-воркер |
| table | CPU | thread | CPU-процесс-воркер (контуры — Python; cell-OCR внутри зовёт Tesseract) |
| OCR | CPU | process | thread-воркер (Tesseract форкается сам) |
| orientation | GPU | — | GPU-воркер (батч по типу) |
| layout | GPU | — | GPU-воркер (батч по типу) |

## 9. Граф исполнения и модель передачи данных (уточнение)

### Граф исполнения — НЕ фиксирован, задаётся конфигом
Граф **не закреплён жёсткой структурой в коде** — он определяется конфигом: списком **blockers** каждой
задачи и тем, **какие задачи вообще присутствуют**. Каких-то компонентов может не быть, какие-то могут быть
**переставлены** или выполнены **независимо**. Планировщик просто исполняет полученный граф (наборы
ready/waiting/done по блокерам), ничего про конкретный порядок не зная.

Ниже — **одна из возможных конфигураций (пример-дефолт)**, а не обязательная структура:
```
render -> binarize -> orient_predict -> deskew -> layout -> ocr
                                                       \--> table
```
`render` (растеризация страницы) — голова графа: рендер **ленивый**, страница превращается в картинку этой
задачей по требованию, а планировщик держит одновременно не больше `max_inflight_pages` страниц (память
ограничена числом воркеров, а не размером документа).
В этом примере ocr и table блокируются `layout`; связка orient_predict->deskew естественна по данным
(предсказали угол -> применили); binarize переставляем. В другом конфиге binarize может отсутствовать,
table — идти независимо от layout, порядок препроцессинга — другой, и т.д. Это дело **конфига, а не кода**.

### Данные: по пайплайну течёт один документ, стадии его дополняют
Payload каждой задачи — **один объект-документ страницы** (dict). Каждая стадия читает нужные поля и
**дополняет** документ своими результатами: `orient_predict` кладёт `columns/angle`, `deskew` — повёрнутое
изображение, `layout` — регионы/вложения и «очищенное» изображение, `ocr` — `lines`, `table` — `tables`.
Так пропадает проблема cross-cutting данных (OCR берёт всё нужное из документа), и граф остаётся простой
цепочкой с fan-out в конце (все задачи одно-блокерные).

- **Большие numpy** (изображение) передаются между процессами через **shared memory**; прочие поля — обычным путём.
- **Пропуск/отказ стадии** (из §7 п.6): дальше передаётся **валидный документ**, просто без доп. обработки;
  недостающие поля **дефолтятся пустыми** в тех стадиях, которые их читают.
- **Fan-out** `layout -> {ocr, table}`: каждый лист получает копию документа после layout и дополняет своим
  (ocr -> lines, table -> tables). Ридер собирает финальный per-page результат из листовых документов.

## 10. Статус реализации (2026-07-01)

**Инфраструктура (готово, 18 юнит-тестов):**
- `shared_image.py` — numpy через shared memory (родитель владеет сегментами).
- `executor.py` — `LocalExecutor` (потоки) и `ProcessExecutor` (персистентные процесс-воркеры: `initializer`
  грузит модели 1 раз, хендлеры по имени, изображения через shm в т.ч. внутри dict-документа, self-fork → потоки,
  GPU → 1 процесс-воркер с батчем по типу).
- `scheduler.py` — граф по блокерам (ready/waiting/done), приоритет=глубина, pass-through при отказе,
  GPU-батч по типу + флаш по таймауту, инъекция executor.

**2c (готово):** `pdf_stages.py` — 6 стадий `process(config,doc)->doc` поверх одного `PdfImageReader`,
и **config-driven** `build_specs` (стадии присутствуют по параметрам, blockers = дефолт §9 на присутствующих).
`PdfImageReader._process_pages_via_stages` под флагами `use_stage_pipeline` / `stage_pipeline_processes`;
per-page результат собирается в форму `_process_one_page`, поэтому барьеры `_parse_document` не тронуты.
**Оба пути (Local и Process) дают выход, ИДЕНТИЧНЫЙ монолитному ридеру** (проверено на BDLCM и CatalanaOccidente,
включая байт-в-байт совпадение sha256 текста и таблиц против чистого master на 24 страницах с таблицами).

Нюанс, найденный бенчмарком: по буквальному §9 `ocr` и `table` — сёстры под `layout`, но тогда OCR читает
картинку без маскирования таблиц и текст ячеек попадает и в тело. Для совпадения с эталонным ридером в
`build_specs` по умолчанию `ocr` блокируется `table` (table пробрасывает очищенную картинку) — т.е.
`... -> table -> ocr`. Сёстринский вариант (быстрее, но с дублированием текста таблиц) остаётся конфигурируемым.

**Сделано доводкой:** персистентный executor (строится один раз на ридере, воркеры держат модели тёплыми —
cold→warm на BDLCM 2 стр.: 15.3→7.9с); настоящий single-forward GPU-батч ориентации (`ColumnsOrientationClassifier.predict_batch`),
паритет sha256 сохранён.

**На реальном GPU (RTX 3080, CatalanaOccidente 24 стр., warm, `OMP_THREAD_LIMIT=1`, `config["on_gpu"]=True`):**
orient уходит на единственный GPU-воркер батчем → серийное CPU-узкое место снято → появляется масштабирование:
proc=1 → proc=8 = **82.3с → 42.6с (×1.93)**; proc=8 GPU (42.6с) в ~1.55x быстрее proc=8 CPU (66.1с) и ~2.2x
быстрее оригинала master на CPU (95.7с). Выход **байт-в-байт** совпадает (`text_sha=03651099fdb2`). Холодный старт
CUDA (~13–24с) платится один раз и амортизируется персистентным executor (cold 66.9 → warm 42.6). Только GPU-воркер
получает `on_gpu=True` (CPU-воркеры — нет, чтобы не плодить CUDA-контексты).
**Ленивый рендер (сделано):** `render` — первая per-page задача (Poppler по одной странице), плюс оконный
приём страниц в планировщике (`max_inflight_pages`): одновременно рендерится/живёт не больше N страниц, а не
весь документ. Паритет sha256 сохранён (per-page рендер идентичен chunked `_split_pdf2image`).

**Осталось:** прогон layout(RT-DETR) end-to-end; стрип неиспользуемой картинки из выходов листовых стадий;
чистая отмена = kill группы процессов (task #5).
